# 복작소 신규 회원가입·관리자 승인제 설계서

작성: 2026-10-13 · 상태: **설계 확정안 / 구현 및 배포 전** · 실제 서비스 변경 없음

## 목표와 변경 불가 조건

- 신규 이용자: 회원정보 입력(이름·채팅 닉네임·휴대전화 번호·선택 프로필 사진) → SMS 소유 인증 → 일반 회원 등록 \`pending\` → 운영자 승인 \`approved\` → **기존 개별 채팅방 비밀번호 정책을 그대로 적용하면서** 일반 채팅 이용
- 복작소 클럽: 일반 회원 \`approved\` 후에만 기존 \`bokjakso_club_members\`의 **별도 승인** 신청 가능
- 기존 \`chat_profiles\`, \`chat_members\`, \`chat_messages\`, \`bokjakso_club_members\`, \`bokjakso_club_messages\` 데이터 및 프로필 토큰/대화/사진/초대링크 보존. 기존 테이블 파괴적 재작성 금지
- 기존 회원은 검증 가능한 예전 프로필/채팅방 토큰의 서버측 전환으로 계속 이용. **신규 신청자가 기기 로컬스토리지만 조작해 기존 회원으로 위장할 수 없게** 기준시점 서버 스냅샷으로 인정
- PWA 설치 여부와 회원 등록 여부는 별개의 조건. 관리자 로그인은 기존 운영자 인증 유지

## 회원 상태 기계

일반 회원: \`new\` (인증 전, 영속화하지 않거나 만료되는 인증 세션만 사용) → \`pending\` → \`approved\` / \`rejected\` / \`suspended\`. 거절자는 명시적 재신청 규칙에서만 \`pending\`으로 돌아갈 수 있으며 제한자는 운영자가 해제할 때까지 불가.

클럽: 기존 별도 테이블의 \`none\` / \`pending\` / \`approved\` / \`rejected\` / \`suspended\` 상태 그대로. **일반 회원이 승인되어도 클럽 자동 승인은 하지 않는다.** 일반 이용 정지·탈퇴 시 클럽도 이용 차단. 일반 회원 승인 취소가 클럽 회원 기록을 삭제하는 것은 아님.

| 일반 회원 상태 | 일반 채팅방 목록 | 방 입장(개별 비밀번호도 필요) | 클럽 승인 신청 | 클럽 메시지 |
| --- | --- | --- | --- | --- |
| 미가입·SMS 미인증 | 차단 또는 공개 소개만 | 차단 | 차단 | 차단 |
| 승인 대기 | 승인 대기 화면 | 차단 | 차단 | 차단 |
| 거절·이용 정지 | 사유·문의 안내 | 차단 | 차단 | 차단 |
| 승인 | 허용 | 허용 | 허용 | 별도 승인 회원만 허용 |
| 검증된 기존 회원(이관 완료) | 기존처럼 허용 | 기존처럼 허용 | 기존 상태 유지 | 기존 클럽 승인 상태 유지 |

## 사용자가 보는 화면

1. 처음 복작소 \`/\` 또는 방 초대 URL로 방문하면 서버의 회원 상태 조회. 가입 미완료 사용자만 \`회원 등록\` 화면으로 안내. 기존 로그인 회원은 원래 화면 이용.
2. 필드: 이름(비공개), 닉네임(채팅에서 공개), 휴대전화 번호(비공개), 프로필 사진(선택·채팅 참여자에게 공개), 필수 개인정보 안내/동의(목적·항목·보유기간·거부 시 영향), 별도 마케팅 선택동의(기본 해제).
3. SMS 전송 → 인증번호 6자리/3분 만료/재전송 60초 제한/시도 횟수 제한 → 인증 성공일 때만 서버에 회원 승인 신청 생성.
4. \`가입 신청이 접수되었어요. 관리자의 승인을 기다려 주세요.\` 상태. \`승인 상태 새로 확인\` 버튼과 느린 간격의 자동 확인을 함께 제공; 관리자 연락이나 '다시 제출' 버튼의 남용 방지.
5. 승인 확인 후 \`채팅방 들어가기\` 활성화. 기존 방은 별도 비밀번호·기존 입장 세션 정책을 유지.
6. 일반 승인이 없는 동안 클럽 진입 차단. 승인 후에도 클럽 신청/관리자 승인 별개.
7. 관리자 운영 화면: \`회원 관리\` → 대기 / 승인 / 거절 / 정지 / 기록. 기본적으로 이름은 최소 표시하고 전화번호는 \`010-****-1234\`처럼 마스킹. 승인 기록에 운영자 ID, 시각, 상태변경 사유 저장.
8. 이름·휴대전화 번호는 일반 채팅 메시지/상대 프로필·목록/초대 URL/푸시 알림/방 코드·로그에 절대 포함하지 않음.

## 데이터 모델 (새 테이블 제안, 운영 DB에 아직 적용 금지)

\`bokjakso_memberships\`
- \`profile_id uuid primary key references chat_profiles(id)\`: 기존 공통 프로필과 연결
- \`status text check (status in ('pending','approved','rejected','suspended'))\`
- \`requested_at, approved_at, status_changed_at\`; \`approved_by\`는 관리자 식별자(접근통제)
- \`legacy_grandfathered boolean default false\`; \`migration_batch_id\` 및 \`legacy_proof_kind\` (서버 검증과 이력 관리)
- \`consent_version, consent_at\`, 마케팅 선택 동의는 별도 필드
- \`rejection_reason_code\`(일반 이용자에게 개인정보·내부 보안 정보 과노출 금지)

\`bokjakso_member_private\` (비공개, 원칙적으로 서비스 키 API만 접근)
- \`profile_id uuid primary key\`
- \`legal_name_ciphertext\`, \`phone_ciphertext\`: 앱 서버의 별도 키로 암호화, 서버 관리 권한 최소화
- \`phone_lookup_hmac unique\`: 정규화된 전화번호의 keyed HMAC으로 중복 검색. 원문 전화번호 또는 단순 SHA256으로 조회키 생성하지 않음
- \`phone_verified_at\`, \`phone_change_at\`, \`phone_last4\` (필요 시 승인화면에 마스킹해서 표시)
- 삭제·익명화 절차의 로그 및 보존기간 정책 별도

\`bokjakso_phone_challenges\`
- 서버 발행 challenge ID, 암호학적 난수 6자리 OTP에 대한 **키 포함 검증값**, 만료시각, 최대 실패 횟수, 재발송 간격, 소비 여부, IP/전화별 남용 제한
- SMS 비밀 키·실제 인증번호를 브라우저/로그/DB 평문으로 저장하지 않음
- 인증 완료한 challenge는 **1회 사용하고 소진**; 다시 사용 불가

\`bokjakso_membership_audit\`: 승인/거절/정지/복구 이벤트의 관리자·대상·날짜·원인 코드. 연락처 평문은 저장하지 않음.

- 일반 회원 테이블과 기존 **클럽 테이블은 병합하지 않는다.**
- 기존 스키마의 RLS·서버 전용 접근 방식에 맞춰, 일반 앱 클라이언트가 회원 상태를 직접 쓰거나 승인값을 위조하지 못하도록 설정.

## API 설계 (기존 서버의 인증 흐름을 확장하되 새 API 경로 수 최소화)

- \`registration-config/status\`: 현재 사용자 프로필 토큰을 서버에서 확인해 \`not_registered|pending|approved|rejected|suspended\`만 반환. 다른 회원 정보·실명·전화번호 미포함.
- \`registration-sms-start\`: 전화번호 정규화, SMS 호출(비밀키 서버만), 횟수제한, 임시 challenge 생성. 너무 상세한 기존 가입 여부 응답 금지.
- \`registration-sms-verify\`: challenge ID + OTP의 서버 검증, 성공 시 짧은 수명 가입용 권한만 발행.
- \`registration-submit\`: SMS 인증 완료 권한+이름+닉네임+동의 버전(사진은 기존 업로드 절차)을 서버 검증; 기존 프로필이 있으면 해당 소유 증명 필요, 없으면 프로필 생성 후 \`pending\`; 승인값은 절대 클라이언트 입력 받지 않음.
- \`registration-review-list/review-update\`: 기존 운영자 로그인 토큰 **및 서버측 운영자 권한** 검증, 상태 변경·감사로그 기록, CSRF/중복 승인 방지.
- \`registration-recovery\`: 기기 분실·변경 시 번호 재인증. **전화번호만으로 기존 프로필 자동 병합 불가**, 추가 확인 및 재발급 정책 필요.

**우회 방지 필수:** 공개 화면만 숨기는 것은 보안이 아님. 서버에서 \`chat-join\`, 이전 세션을 이용한 \`chat-list\`, \`chat-send\`, 채팅 사진 인증/업로드, 사진 삭제, 알림 등록 및 채팅방 멤버 관련 모든 기능의 실효 권한을 승인 상태로 확인. 승인 취소 즉시 기존 세션도 더 이상 메시지를 열람/전송하지 못하게 서버에서 막기. 클럽 API는 일반 회원 \`approved\`와 클럽 \`approved\` 둘 다 확인.

## 기존 회원 무손실 이행

- **1단계:** 읽기 전용 현황 수집 + DB 스냅샷/백업 + 기존 프로필·개별 채팅방·클럽 연결 무결성 점검.
- **2단계:** 새 테이블만 추가(기존 5개 테이블이나 대화 메시지 수정 없음). 운영용 관리자 로그인/상태검증 경로부터 만들고 테스트.
- **3단계:** 강제승인 시행 *직전*의 서버 기록 기준으로 기존 유효한 프로필 ID와 검증 가능한 chat_members 토큰의 대상 목록을 확정; 검증된 레거시 기존 회원만 \`approved + legacy_grandfathered=true\`로 이관. 브라우저 로컬 값 자체는 승인 증거가 아님. 프로필 없는 레거시 이용자는 기존 방 토큰과 서버 회원 기록을 통해 안전하게 연결할 수 있어야 하며, 자동 연결할 수 없으면 운영자 복구 절차로 별도 보호.
- **4단계:** 기존 회원의 최초 재방문 시 추가 실명/번호 강제 수집하지 않고 원래 대화와 이용 권한 유지. 필요한 경우 추후 개인정보 목적 안내를 하고 자발적·단계적 전환을 별도 정책으로 실행.
- **5단계:** 신규 일반 회원에게만 회원가입·SMS·승인제 강제하는 기능 플래그 점진 적용. 기존 데이터 쓰기/읽기 테스트, 되돌리기 시 신규 가입 차단 플래그만 해제(데이터 삭제 금지).
- **6단계:** 기존에 승인된 클럽 회원은 그대로 유지; 새 일반 회원 승인이 완료되어도 클럽 신청은 \`pending\`부터 시작.
- 이후 계정 통합은 증거를 갖춘 서버측 병합/고객지원 처리만 허용. 임의로 채팅 작성자 ID나 이전 메시지를 바꾸지 않음.

## 보안·개인정보·운영 출시 차단 조건

- SMS 발송업체 및 등록된 발신번호 계약, 발송 요금/한도, 전송 키의 비밀관리, 실패·재시도 정책 정해지기 전에는 발송 UI를 실제 동작시키지 않음.
- 전화번호 인증은 번호 점유 확인이며 **실명 확인은 아님**. 실명 신뢰가 필요하면 별도 본인확인 서비스 검토.
- 개인정보 수집 목적·항목·보유기간·서비스 운영자 정보·처리위탁/국외이전 필요 여부·탈퇴/삭제 및 열람정정 안내·약관/개인정보처리방침 링크를 운영자가 확정해야 함.
- 전송 구간 HTTPS, 휴대폰·번호의 서버 측 암호화/키 분리, 불필요한 접속로그와 디버깅 출력 금지, 관리자 권한 최소화 및 감사로그, 관리자 2단계 인증을 권장.
- 미인증 사용자·승인 대기자·거절자·정지자가 기존 방 초대 링크/구버전 앱/직접 API 요청/기존 세션 재사용으로 채팅을 볼 수 없는지 테스트.
- 오류 시 **실패 안전(fail closed)**: 회원 승인 상태를 검증할 수 없으면 신규 일반회원에게 채팅 권한을 허용하지 않음. 검증된 기존 회원 무손실 전환도 검증해야 출시 가능.
- 기존 PWA의 설치·개별 방 비밀번호·초대 링크·이미지 업로드·알림·관리자 클럽 기능은 회귀 테스트.

## 실제 구현 일정의 단계 구분

1. 화면 미리보기: \`chat-pwa/signup-preview.html\` 존재(회원가입/문자 인증/서버 저장은 미구현).
2. 인증 공급업체 연결과 개인정보 정책 확정.
3. DB 마이그레이션(신규 전용 테이블) → API 인증·권한 → 관리자 승인 화면 → 기존 회원 이관.
4. 개발/스테이징 환경에서 전체 가입/승인/거절/정지·클럽 별도 승인·기존 회원·개별 방 비밀번호·복구·탈퇴 검증.
5. 운영자 승인 받은 후 운영 릴리스.

**이 설계서만 GitHub에 저장하는 것은 서비스를 변경하지 않는다.** 실제 회원가입 기능과 SMS 비용이 발생하는 운영 처리는 별도 개발·테스트·배포 후에만 적용한다.
